# Changelog

## [Unreleased]

### Added

- Initial release: `Scry.Engine.MongoDB` -- a real `Scry.Core.EngineBehaviour` implementation over MongoDB, via `mongodb_driver`. Replaces `scry_document`'s own in-memory reference implementation (`Scry.Document.Executor`, a plain `%{path => rows}` map) with genuine collection-backed `DEEP`/`PARENT`/`SIBLINGS`/`ANCESTORS` execution against a real document store -- the `document` kind's first real adapter, closing the same kind of gap `scry_engine_neo4j` closed for `graph` one round earlier. Like `scry_search`/`scry_graph` (replaced by `scry_engine_elasticsearch`/`scry_engine_redisearch`/`scry_engine_neo4j`), `document` has no separate engine tier in its own reference form, so this package implements `Scry.Core.EngineBehaviour` directly too.
  **Collection-per-tree-key**: the reference model's own `["library", "catalog", "fiction"]`-style tree-position keys map onto one real MongoDB collection per key, its own name the segments joined with `.` -- confirmed directly that a real `.`-containing collection name inserts and queries correctly, no escaping needed. `DEEP`'s own cross-key matching and `PARENT`/`SIBLINGS`/`ANCESTORS`'s own relative-key resolution both become "enumerate every real collection name (`db.listCollections()`), filter client-side by the identical logic the reference `Executor` already uses, then fetch the matched collection(s)".
  **No pushdown at all**: every one of `WHERE`/`GROUP BY`/aggregates/`HAVING`/`DISTINCT`/`ORDER BY`/`LIMIT`/`OFFSET`/projection applies generically via `Scry.Core.QueryOps.run_flat/3`, never translated into a MongoDB query filter -- the only real adapter-specific work is knowing which collection(s) to read, since MongoDB's own filter language has nothing structural to contribute to `DEEP`/`PARENT`/`SIBLINGS`/`ANCESTORS` resolution itself. `_id` (a real `%BSON.ObjectId{}` struct the driver always attaches) is stripped from every row before it reaches the pipeline, since the reference model's own rows have no implicit `"_id"` field at all.
  **One real driver finding, not assumed**: `Mongo.command/3` requires its own `cmd` argument as a keyword list, not a plain map -- confirmed directly, a `%{dropDatabase: 1}` map crashes with a `FunctionClauseError` inside `mongodb_driver`'s own session handling, while `[dropDatabase: 1]` works correctly.
  **One stated, deliberate divergence**: a collection matching no document at all -- or that doesn't exist yet -- is simply an empty result, not an error (confirmed directly, `Mongo.find/4` against a nonexistent collection returns `[]`), where the reference's own `resolve_source/3` errors for an absent source -- the identical divergence `scry_engine_neo4j` already states for a label matching no node.
  **Parity tested against the reference**: AGENTS.md's "Parity between multiple implementations" rule applied directly -- the same parsed `DEEP`/`PARENT`/`SIBLINGS`/`ANCESTORS` queries run against both a real MongoDB container and `scry_document`'s own in-memory reference `Executor`, asserting matching results.
